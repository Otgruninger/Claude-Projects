01

The scope decision

Your store listing currently promises no ads, no data collection. That claim is true today because nothing leaves the browser, and it is a genuine differentiator against UpAhead’s account model. The moment you add server sync you must update your Chrome Web Store data-use disclosures, and the claim in your listing copy stops being accurate.

That is not a reason to never build the backend — it is a reason not to bundle it into the same release as four features that need no such change. Ship the local tier now, keep the disclosure untouched, and make the backend its own release where the privacy rewrite gets handled deliberately instead of as a footnote.

In — this release

Runs entirely in the extension. No new data leaves the browser, so no disclosure change.

  • Weighted grade engine with target-score projection — the headline feature, and the one you can do better than UpAhead because the numbers come from the real gradebook
  • Today view, streaks, completion ritual — cheapest work here, biggest effect on renewal
  • Syllabus parsing upgrade — category weights, meeting times, office hours
  • ICS export — one-time download, no server required

Out — needs a backend

Each requires a server-side copy of the data. All four become straightforward once that exists.

  • Sync account — the architectural unlock the rest depend on
  • Email & SMS reminders — must fire with the browser closed
  • Live ICS subscription feed — needs a hosted, authenticated URL
  • Parent dashboard — needs accounts, a web surface, and consent state
02

Build order

Sequenced by dependency, not by value. Phase 0 looks like overhead and is the most important thing in this document: it is what makes the backend release cheap instead of a rewrite.

00

Normalize the item model and give everything a stable ID

Size S–M Blocks every phase below Ships invisible

One internal shape for every tracked thing, whatever its origin — Brightspace assignment, quiz, exam, lab, Gradescope import, syllabus-derived row, or hand-added task. Every item carries a stable identity and a provenance field. Without this, completion state resets on re-scrape, ICS re-import duplicates events, dedupe is guesswork, and the sync release becomes a migration project.

Work
  • Define one item schema: id, courseId, title, type, dueAt, points, weightCategory, source, completedAt, userEdited.
  • Stable ID scheme — derive from the LMS org unit and item id where available (d2l:{orgUnitId}:{itemId}), and from a hash of normalized title plus due date for syllabus-derived rows.
  • Keep user state in a separate keyspace from scraped data, joined by id, so a re-scrape never clobbers completions, edits, or dismissals.
  • Write a one-time migration from your current storage shape, and version the schema so the next one is easier.
  • Add a source value per item and surface it in the UI — students should be able to tell a scraped deadline from a syllabus-guessed one.
Done when
  • Re-scraping a course preserves every completion and manual edit
  • The same assignment seen via Brightspace and via syllabus parsing resolves to one item, not two
  • Existing users’ data migrates with no visible loss on update
  • Schema version is stored and checked at load
Risk

Migration bugs hit existing paying users on auto-update, silently. Write the migration defensively: keep a backup copy of pre-migration storage for one version so you can recover a user who reports losses, and test against real exported storage from a live install, not synthetic fixtures.

01

Grade scraper and calculation engine

Size L Depends on 00 highest value

Headless first — no UI in this phase. Extract the gradebook and compute a grade you can defend, with the calculation logic isolated and unit-tested so the messy cases are provable rather than hoped-for. The engine must be able to say “I don’t know”; a confidently wrong GPA number is worse for you than an absent one.

Work
  • Scrape the student grades page per course: item name, category, points earned, points possible, category weights, item status (graded, ungraded, exempt, dropped), and the course’s grading scheme for letter cutoffs.
  • Prefer the JSON the page itself calls over DOM parsing where you can find it — it survives institutional theming that breaks selectors.
  • Implement both calculation modes: weighted (sum of category weight × category percentage) and points (total earned over total possible). Courses use one or the other; detect which.
  • Compute and expose two current grades: graded-items-only, and assuming zeros for everything ungraded. Students routinely confuse these and Brightspace shows only one.
  • Handle drop-lowest rules, exempt items, extra credit that pushes a category past 100%, and bonus categories.
  • Target projection: given a target percentage, solve for the required average on remaining weight. Report unreachable targets plainly (“you would need 112% — not reachable”) rather than clamping silently.
  • Fall back to syllabus-derived weights (phase 03) when the professor never configured the gradebook, and mark the result as estimated.
Done when
  • Computed grade matches Brightspace’s own displayed calculated grade on every test course
  • Unit tests cover weighted, points, drop-lowest, exempt, extra-credit, and empty-gradebook cases
  • Engine returns an explicit unknown state rather than a number when inputs are incomplete
  • Target projection is correct against a hand-computed worked example
Risk

This is a much more fragile scrape than due dates, and the failure mode is a wrong number a student makes decisions on. Build a self-check: compare your computed grade against the grade Brightspace displays, and if they disagree, hide the card and show a “can’t verify this course” state instead of your number. That single guard converts your worst-case bug from a trust-destroying error into a graceful gap.

02

Grade UI — dial, breakdown, target slider

Size M Depends on 01 Ships the hero screenshot

The feature students will actually describe to their friends. UpAhead’s release notes lead with their circular grade display, which tells you what they think sells it. The interaction, not the number, is the demo: dragging a target and watching required scores move is what makes this feel like a tool rather than a readout.

Work
  • Per-course circular dial showing percentage and letter grade together — students think in letters, and the letter is what makes it glanceable.
  • Category breakdown: how much each assignment type contributes, and how much weight is still unspent.
  • Target as a slider, not a form field. Drag to a target letter or percentage, see the required average on remaining work update live.
  • Show provenance inline — a quiet label for whether weights came from the gradebook or the syllabus.
  • Handle the empty and unknown states with real copy: no grades posted yet, gradebook not configured, couldn’t verify.
  • Respect prefers-reduced-motion on the dial animation.
Done when
  • Dial renders correctly at every state including 0%, >100%, and unknown
  • Slider updates required-score figures without a reload
  • Estimated-weight courses are visually distinct from verified ones
  • New store screenshots captured from this view
Risk

Scope creep into a full grade-history graph. Not this release — it needs time-series data you are not yet storing, and it does not sell the feature the way the projection does.

03

Syllabus parsing: weights, meeting times, office hours

Size M Feeds 01 privacy fork

You already pull deadlines out of syllabus PDFs. UpAhead pulls three more things from the same document, and one of them — the grading breakdown with category weights — is what keeps phase 01 working for the very common case of a professor who never set up the Brightspace gradebook.

Work
  • Extract the grading table: category name to weight percentage. Validate that weights sum to ~100 and flag when they don’t.
  • Extract class meeting times and professor office hours — cheap once you are already parsing, and they turn the product from a deadline list into a daily reference.
  • Accept pasted text and screenshots, not only PDF upload. Many syllabi live inside a Brightspace content page your extension can already read.
  • Mandatory review-and-edit step before anything is committed. This converts a parsing miss from a broken product into a five-second correction, and UpAhead leans on it heavily.
  • Reconcile against LMS-scraped items: dedupe on normalized title similarity plus due-date proximity, and prefer the LMS date when they disagree — professors update Brightspace, not the PDF.
Done when
  • Weights extracted from a real syllabus flow into the grade engine as estimated weights
  • Review step lets a student fix any field before commit
  • Re-importing the same syllabus produces no duplicates
  • Weight totals that don’t sum to 100 are surfaced, not silently normalized
Risk

Check where your parsing actually runs. If syllabus text is already being sent to an API for extraction, then content is leaving the browser today and the “no data collection” line in your listing needs revisiting this release, independent of everything else here. If parsing is local, keep it local — it is a real differentiator and MV3 forbids remote code anyway.

04

Today view, streaks, completion ritual

Size S Depends on 00 Drives renewal

You ship four views as equals; UpAhead ships one opinionated default. A tracker consulted twice a semester does not get renewed — a tracker with a satisfying daily check-in does. Cheapest phase here and the one most directly tied to a semester license renewing.

Work
  • Make Today the default view, keeping the other three available. Sections in order: overdue (in the alarm color), due today, due this week, then everything else.
  • Streak counts days checked in, not days cleared. Punishing a heavy week is how you destroy the habit you just built. Store the local date, handle timezone changes, and don’t reset on a single miss without a grace day.
  • To Do / Completed tabs, and a completion interaction that feels like something — a real animation, a count visibly moving.
  • Completion state persists across re-scrape via the phase 00 keyspace split.
  • Keyboard-accessible completion, with visible focus states.
Done when
  • Opening the extension lands on Today with overdue work first
  • Streak survives browser restart, timezone change, and re-scrape
  • Completing an item is reversible and animates
  • All three other views still reachable in one click
Risk

Low. The only real trap is a streak that resets unfairly and reads as punitive — test the day-boundary and timezone cases specifically, since they will hit every user eventually and you will never reproduce them by hand.

05

ICS export

Size S Depends on 00 Preview of the live feed

The no-backend half of the calendar story. A generated .ics file the student imports once into Google, Apple, or Outlook. It is a snapshot rather than a live subscription — say so in the UI — but it closes most of the practical gap now and the serializer you write here is exactly the one the hosted feed will use later.

Work
  • Serialize items to valid iCalendar. Generate in-page as a blob and download via an anchor — do not add the downloads permission for this (see the release checklist for why).
  • Stable UID per item, derived from the phase 00 id, so a later re-import updates events instead of duplicating them.
  • Timed deadlines as timed VEVENTs; date-only deadlines as VALUE=DATE all-day events. Get DTSTAMP and timezone handling right.
  • Sensible VALARM defaults, course code in the SUMMARY so it reads well in a crowded week view, and a link back to the Brightspace item in the DESCRIPTION.
  • Let the student choose which courses to include before export.
Done when
  • Exported file imports cleanly into Google Calendar, Apple Calendar, and Outlook
  • Re-importing after a change updates events rather than duplicating them
  • All-day and timed events land on the correct date across timezones
  • UI states plainly that this is a snapshot, not a live sync
Risk

Timezone and all-day handling is the classic source of “my assignment shows on the wrong day” bug reports. Test explicitly with a machine set to a non-UTC timezone, and with a deadline at 11:59pm — that is the one that slips a day.

03

The risk that spans every phase

Brightspace is not one target. Every institution runs its own instance, on its own D2L version, with its own theming, widget layout, and enabled features. Your due-date scraping already survives this or you would not have shipped — but a gradebook scrape touches far more institution-specific surface, and phase 01 is where per-school variance will bite.

Four mitigations, in order of value. Prefer the page’s own JSON endpoints over DOM selectors, since markup is what institutions customize. Feature-detect and fail soft — hide the grade card rather than render a guess. Put a visible “grades look wrong?” report path directly on the grade card, because you will learn about breakage from users or not at all. And use a staged rollout so a scrape failure at one school does not reach your whole install base at once.

04

Release checklist

The permissions line is the one that can actually hurt you, so take it first.

Adding a permission disables your extension until every existing user re-accepts it. Chrome shows a re-consent prompt on update for newly requested permissions, and the extension sits inert until the user clicks through. On a paid install base that is a support event and a churn event. Nothing in phases 00–05 requires a new permission if you generate the ICS as a blob rather than reaching for chrome.downloads — keep it that way, and if a phase seems to need one, redesign the phase before you accept the prompt.

Manifest & policy

  • No new permissions or host permissions vs. current published version
  • No remotely hosted code — all logic bundled (MV3 requirement)
  • Version bumped; changelog written
  • Any new library vendored, not CDN-loaded

Privacy disclosure

  • Data-use disclosures reviewed — unchanged if everything stayed local
  • “No data collection” claim re-verified against phase 03 parsing path
  • Listing copy still accurate after the feature additions

Store listing

  • New screenshots led by the grade dial and target slider
  • Pricing copy contradiction resolved — semester renewal or permanent license, stated once
  • Gradescope import surfaced prominently; it is a real differentiator
  • Description updated with grades and calendar export

QA before submit

  • Tested against at least three different institutions’ Brightspace
  • Upgrade path tested from the currently published version with real user data
  • Weighted, points-based, and unconfigured gradebooks all verified
  • Non-UTC timezone pass on due dates and ICS export
  • Staged rollout enabled if available
05

What the next release after this one looks like

Not this cycle, but worth knowing where phase 00 is pointing. The sequence below is the backend track, and it is deliberately ordered so the privacy rewrite happens once, at the start, rather than accreting.

Release B · foundation

Sync account

Extension becomes a client; server holds a normalized copy. Opt-in, local-only by default. This is where the privacy disclosure changes and where the listing copy gets rewritten honestly.

Release B · immediately after

Email reminders

A cron job and a template. Covers most of the reminder value with none of the SMS friction. Ship in the same release as sync so the account has an obvious payoff.

Release C

Live ICS subscription feed

Reuses the phase 05 serializer behind a revocable signed URL. Subscriptions stay live, so every scrape updates the student’s real calendar.

Release C

Parent view & gift plan

Three independent consent toggles, grades behind an extra confirmation, revocable anytime. The commercial point: the parent pays.

Later, if at all

SMS

Gated behind 10DLC brand and campaign registration — weeks of paperwork and per-message cost. Paid tier only, and only once email proves the demand.
